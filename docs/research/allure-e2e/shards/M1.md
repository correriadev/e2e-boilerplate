## 1. Executive Summary

- **[M1.1]** O Allure 3 monta a árvore pelo parâmetro `groupBy`, uma lista de nomes de label; os presets oficiais são suite-based (`parentSuite`, `suite`, `subSuite`) e BDD (`epic`, `feature`, `story`), e a hierarquia suite-based tem no máximo três níveis. — *Confidence:* `verified` | *Sources:* `https://allurereport.org/docs/v3/configure/ (2026-11-13)`, `https://allurereport.org/docs/v3/navigation/ (2026-11-13)` | *Deep Dive:* `#m1-1`
- **[M1.2]** A doc define epic como conjunto grande de features, feature como conjunto de user stories e story pelo comportamento esperado em cenários; não traz recomendação para E2E de API, então o mapeamento para API é inferência própria. — *Confidence:* `inferred` | *Sources:* `https://allurereport.org/docs/v3/navigation/ (2026-11-13)` | *Deep Dive:* `#m1-2`
- **[M1.3]** `severity` aceita exatamente `trivial`, `minor`, `normal`, `critical` e `blocker`; `owner` é texto livre do responsável pela estabilidade do teste; `tags` listam as features testadas, sem lista fechada na doc; critério oficial por nível de severity não consta. — *Confidence:* `verified` (severity, owner); `inferred` (tags) | *Sources:* `https://allurereport.org/docs/v3/readability/ (2026-11-13)`, `https://allurereport.org/docs/xunit-reference/ (2026-11-13)` | *Deep Dive:* `#m1-3`
- **[M1.4]** A doc de Allure 3 define `ID` como identificador único (usado por ferramentas como Allure TestOps) e links de tipo issue e TMS com template de URL a partir de identificador curto; no adaptador .NET, `AllureId`, `AllureLink`, `AllureIssue` e `AllureTms` expressam isso; vínculo próprio com requisito não é tratado. — *Confidence:* `verified` | *Sources:* `https://allurereport.org/docs/v3/readability/ (2026-11-13)`, `https://allurereport.org/docs/xunit-reference/ (2026-11-13)` | *Deep Dive:* `#m1-4`

### M1.1: Como o Allure 3 monta a árvore a partir de parentSuite, suite, subSuite e de epic/feature/story?

- **Verdict:** A árvore não tem estrutura fixa. O plugin Awesome recebe `groupBy`, uma lista de nomes de label (`Array of label names`). Os presets oficiais são suite-based (`parentSuite`, `suite`, `subSuite`), BDD (`epic`, `feature`, `story`), package-based (`package`, `testClass`, `testMethod`) e module-based (`module` acima dos níveis suite-based). A hierarquia suite-based chega a três níveis. Inferência: como `groupBy` é opção do plugin, o agrupamento é escolhido na configuração do relatório, e o teste apenas declara os labels; a doc não diz isso com essas palavras.
- **Evidence Items:**
  1. **Claim:** O plugin Awesome aceita `groupBy` como array de nomes de label; o preset suite-based é declarado assim.
     - **Excerpt:** "groupBy: ["parentSuite", "suite", "subSuite"];"
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
  2. **Claim:** Allure 3 organiza os resultados por um único parâmetro, `groupBy`.
     - **Excerpt:** "Allure 3 supports a variety of ways to organize the test results, all defined by the groupBy parameter"
     - **Source:** `https://allurereport.org/docs/v3/navigation/ (2026-11-13)` (`verified`)
  3. **Claim:** Na hierarquia suite-based, o total é de até três níveis.
     - **Excerpt:** "for the total of up to three levels of hierarchy"
     - **Source:** `https://allurereport.org/docs/v3/navigation/ (2026-11-13)` (`verified`)
  4. **Claim:** Em cada hierarquia, o autor do teste precisa atribuir campos específicos.
     - **Excerpt:** "For each hierarchy, Allure expects test authors to assign specific fields to the tests."
     - **Source:** `https://allurereport.org/docs/v3/navigation/ (2026-11-13)` (`verified`)
  5. **Claim:** Os valores padrão desses campos podem variar conforme a implementação de cada framework.
     - **Excerpt:** "the implementation may differ in how the default values are chosen for these fields"
     - **Source:** `https://allurereport.org/docs/v3/navigation/ (2026-11-13)` (`verified`)
  6. **Claim:** O preset de módulo acrescenta `module` acima dos níveis suite-based.
     - **Excerpt:** `groupBy: ["module", "parentSuite", "suite", "subSuite"];`
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
  7. **Claim:** O primeiro label da lista é o nível mais externo da árvore.
     - **Excerpt:** (sem trecho de origem; derivado da ordem dos presets no item 6)
     - **Source:** inferido a partir dos itens 1 e 6 (`inferred`)
- **Gaps / Edge Cases:**
  - Valor padrão do `groupBy` do plugin Awesome não consta nas páginas consultadas. O padrão `"suite"` que aparece na doc é do Log plugin, outro plugin.
  - Não verifiquei como o adaptador .NET preenche `parentSuite`, `suite` e `subSuite`; a página de referência do adaptador consultada não tratou desse ponto.
  - Comportamento com teste sem suite ou sem parent suite não foi consultado.

### M1.2: Qual semântica a documentação recomenda para epic, feature e story em testes E2E de API?

- **Verdict:** A doc define os três termos de forma genérica, sem contexto de API. Epic é um conjunto grande de features que o time desenvolve e testa; feature é um conjunto de user stories; story descreve como o software deve se comportar em cenários diferentes. Não há recomendação para E2E de API. O mapeamento sugerido (epic = domínio ou produto, feature = capacidade ou endpoint, story = cenário de negócio) é inferência minha, não recomendação oficial nem prática de blog consultada.
- **Evidence Items:**

### M1.3: Quais são owner, tags e severity, com valores aceitos e uso recomendado?

- **Verdict:**

  - **severity:** valores aceitos exatamente `trivial`, `minor`, `normal`, `critical`, `blocker`. A doc diz que serve para priorizar a investigação de falhas. Adaptador .NET: `AllureSeverity(SeverityLevel value)`.

### M1.4: Como IDs estáveis e vínculos com requisito são expressos (AllureId, AllureTms, AllureLink, AllureIssue)?

- **Verdict:** `ID` é o identificador único do teste, que ferramentas como Allure TestOps podem usar. No adaptador .NET é `AllureId(string value)`. Vínculos são links com tipo: web, issue tracker (`issue`) e TMS (`tms`). A integração aceita identificador curto e gera a URL por template, por exemplo `BUG-123`. No .NET: `AllureLink(string name, string url)`, `AllureIssue(string name)` e `AllureTms(string name)`. Não há tipo próprio de requisito; o mais próximo é link de issue ou TMS.
- **Evidence Items:**
  1. **Claim:** ID é o identificador único do teste.
     - **Excerpt:** "Unique identifier of the test."
     - **Source:** `https://allurereport.org/docs/v3/readability/ (2026-11-13)` (`verified`)
  2. **Claim:** O ID pode ser usado por outras ferramentas, como o Allure TestOps (página cross-versão).
     - **Excerpt:** "The ID can be used by additional tools such as Allure TestOps."
     - **Source:** `https://allurereport.org/docs/v3/readability/ (2026-11-13)` (`verified`)
  3. **Claim:** No adaptador .NET, o ID é definido por atributo com texto.
     - **Excerpt:** "[AllureId(string value)]"
     - **Source:** `https://allurereport.org/docs/xunit-reference/ (2026-11-13)` (`verified`, cross-versão)
  4. **Claim:** Um tipo de link é o link para issue no issue tracker do produto.
     - **Excerpt:** "a link to an issue in the product's issue tracker;"
     - **Source:** `https://allurereport.org/docs/v3/readability/ (2026-11-13)` (`verified`)
  5. **Claim:** Outro tipo de link é o link para a descrição do teste em sistema de gestão de testes (TMS).
     - **Excerpt:** "a link to the test description in a test management system (TMS)."
     - **Source:** `https://allurereport.org/docs/v3/readability/ (2026-11-13)` (`verified`)
  6. **Claim:** Identificador curto é convertido em URL completa por template configurado na integração.
     - **Excerpt:** "an identifier BUG-123 can automatically turn into https://bugs.example.com/BUG-123"
     - **Source:** `https://allurereport.org/docs/v3/readability/ (2026-11-13)` (`verified`)
  7. **Claim:** No .NET, há atalhos para os tipos de link issue e tms.
     - **Excerpt:** "For convenience, Allure provides shorthand attributes and methods with pre-selected link types: `issue` and `tms`."
     - **Source:** `https://allurereport.org/docs/xunit-reference/ (2026-11-13)` (`verified`, cross-versão)
  8. **Claim:** No .NET, link genérico recebe nome e URL.
     - **Excerpt:** "[AllureLink(string name, string url)]"
     - **Source:** `https://allurereport.org/docs/xunit-reference/ (2026-11-13)` (`verified`, cross-versão)
  9. **Claim:** Vínculo com requisito seria expresso como link de issue ou TMS.
     - **Excerpt:** (sem trecho de origem; derivado dos itens 4 a 7)
     - **Source:** inferido a partir dos itens 4 a 7 (`inferred`)
- **Gaps / Edge Cases:**
  - Vínculo com requisito como label próprio não é tratado nas fontes; a resposta é inferência via issue ou TMS.
  - Não verificado se o adaptador .NET grava `AllureId` como label de nome próprio. O exemplo de `hideLabels` cita `/^allure_id/`, o que sugere isso, mas não confirma.
  - Estabilidade do ID entre execuções (histórico) não é tratada na doc consultada.

### M1.5: Quais labels o adaptador .NET adiciona automaticamente (host, thread, package, language, framework) e como ocultá-las?

- **Verdict:** Não encontrei, nas páginas consultadas, lista de labels adicionados automaticamente pelo adaptador .NET. Host, thread, package, language e framework não são confirmados como automáticos. Para ocultar, o Allure 3 documenta `hideLabels`: lista de nomes de label (ou regex) que só afeta a exibição na UI e não filtra testes. Labels cujo nome começa com `_` ficam sempre ocultos. O exemplo oficial cita `package`, `thread` e `/^allure_id/`, mas o exemplo não afirma que o adaptador gera esses labels.
- **Evidence Items:**
  1. **Claim:** `hideLabels` oculta labels da UI do relatório pelo nome.
     - **Excerpt:** "Hides labels from the report UI by label **name**."
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
  2. **Claim:** `hideLabels` não filtra testes; afeta só a exibição.
     - **Excerpt:** "Does not filter tests out - only affects what is displayed."
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
  3. **Claim:** Labels com nome iniciado por `_` são sempre ocultos, independentemente da configuração.
     - **Excerpt:** "Labels whose name starts with `_` are always hidden regardless of this setting."
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
  4. **Claim:** Exemplo oficial de configuração de `hideLabels` com nomes e regex.
     - **Excerpt:** `hideLabels: ["package", "thread", /^allure_id/]`
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`, exemplo)
- **Gaps / Edge Cases:**
  - Lista de labels automáticos do adaptador .NET não confirmada. As duas páginas consultadas (configure e xunit-reference) não tratam do tema. Não consultados: referência NUnit (`https://allurereport.org/docs/nunit-reference/`) e MSTest; cabe checar nelas.
  - Não verificado se `hideLabels` atua sobre labels gerados pelo adaptador .NET; não testado.
  - O exemplo com `/^allure_id/` é exemplo oficial, não validado contra saída real.
