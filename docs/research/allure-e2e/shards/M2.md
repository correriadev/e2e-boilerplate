### M2.3: Como funcionam categories: regras, matchers, groupBy e padrões?
- **Verdict:** `categories` é objeto `{ rules: [...] }`. Cada regra exige `name` e `matchers`; `id` é opcional (cai para `name`; ids iguais são mesclados). Regras são avaliadas na ordem definida e o teste casado é consumido. Matcher de objeto faz AND entre campos (`statuses`, `flaky`, `labels`, `message`, `trace`, `transitions`, `environments`); array de matchers faz OR; função `(data) => boolean` exige config dinâmica. `groupBy` aceita strings built-in ou `{ label }`, com `groupByMessage`, `groupEnvironments`, `expand` e `hide`. Os defaults "Product errors" e "Test errors" pegam o que sobra.
- **Evidence Items:**
  1. **Claim:** `categories` é um objeto com array `rules`, onde cada item é uma definição de categoria customizada.
     - **Excerpt:** "custom categories are defined in the `categories` configuration field, which is an object with a `rules` array."
     - **Source:** `https://allurereport.org/docs/categories/ (2026-11-13)` (`verified`)
  2. **Claim:** Duas regras com o mesmo `id` são mescladas; sem `id`, o `name` é usado como identidade.
     - **Excerpt:** "Two rules with the same `id` are merged."
     - **Source:** `https://allurereport.org/docs/categories/ (2026-11-13)` (`verified`)
  3. **Claim:** Todos os resultados são casados primeiro contra as regras customizadas, na ordem definida.
     - **Excerpt:** "All test results are matched against custom rules first, in the order defined."
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
  4. **Claim:** Campo `labels` do matcher de objeto casa por expressão regular; `message` e `trace` também casam por regex.
     - **Excerpt:** "matches against labels, as a regular expression"
     - **Source:** `https://allurereport.org/docs/categories/ (2026-11-13)` (`verified`)
  5. **Claim:** Dentro de um matcher de objeto, os campos combinam em AND.
     - **Excerpt:** "Tests fitting all of these conditions will be included (AND logic applies here)."
     - **Source:** `https://allurereport.org/docs/categories/ (2026-11-13)` (`verified`)

  10. **Claim:** `groupByMessage` (default `true`) adiciona um nível de agrupamento por mensagem de erro abaixo dos níveis de `groupBy`.
      - **Excerpt:** "adds an additional grouping level below `groupBy` levels, clustering tests that share the same error message."

### M2.5: Como historyPath, historyLimit e flakyDetection são configurados?
- **Verdict:** `historyPath` (default indefinido) liga o histórico; o arquivo é JSONL único, com uma linha por execução (segundo resumo da página de configuração). Não é mais preciso copiar o histórico para a pasta de resultados. `historyLimit` (default ilimitado) limita execuções consideradas e descarta as mais antigas. `appendHistory` (default `true`) controla se a execução atual entra no histórico. `historyBaseUrl` só vale com `historyPath` e é ignorado se `allureService` estiver configurado (valor não copiado aqui). `flakyDetection` não tem efeito sem histórico; `historyDepth` default 10, `stabilizationPeriod` default 5, `includePassedTests` default `false`. Flaky e transições exigem `historyPath`.
- **Evidence Items:**
  1. **Claim:** `historyPath` é o caminho do arquivo que guarda resultados entre execuções; default indefinido.
     - **Excerpt:** "Path to the history file that tracks test results across multiple runs."
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
  2. **Claim:** No Allure 3, o histórico fica em um único arquivo JSONL. Página cross-versão.
     - **Excerpt:** "now history is stored in a single JSONL file."
     - **Source:** `https://allurereport.org/docs/v3/migrate/ (2026-11-13)` (`verified`; cross-versão)
  3. **Claim:** Para ativar o histórico no Allure 3, basta definir `historyPath`.
     - **Excerpt:** "To enable history in Allure 3, simply set the `historyPath` config parameter."
     - **Source:** `https://allurereport.org/docs/v3/migrate/ (2026-11-13)` (`verified`; cross-versão)
  4. **Claim:** No Allure 2, o histórico era copiado para a pasta de resultados a cada geração; no Allure 3 esse passo não existe mais. Cross-versão.
     - **Excerpt:** "No more need to copy anything anywhere."
     - **Source:** `https://allurereport.org/docs/v3/migrate/ (2026-11-13)` (`verified`; cross-versão)
  5. **Claim:** `historyLimit` (default ilimitado) limita quantas execuções passadas são consideradas; ao exceder, as entradas mais antigas são descartadas.
     - **Excerpt:** "Caps how many past runs are considered." e "the oldest entries are dropped"
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
  6. **Claim:** `appendHistory` (default `true`) decide se a execução atual é acrescentada ao histórico.
     - **Excerpt:** "Whether to add the current run to the history."
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
  7. **Claim:** `historyBaseUrl` só é usado com `historyPath` e é ignorado se `allureService` estiver configurado.
     - **Excerpt:** "Only used with `historyPath`, ignored if `allureService` is configured."
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
  8. **Claim:** `flakyDetection` não tem efeito se não houver histórico.
     - **Excerpt:** "Has no effect if history is not available."
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
  9. **Claim:** `historyDepth` (default 10) é o número máximo de resultados anteriores de um teste que a análise considera.
     - **Excerpt:** "the maximum number of previous results of a test that Allure analyzes."
     - **Source:** `https://allurereport.org/docs/v3/configure/ (2026-11-13)` (`verified`)
